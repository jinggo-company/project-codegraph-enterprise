## 破坏性测试

### DT-01: 双通道容错
- **结果**: ✅ PASS — `Promise.allSettled` 确保一个通道失败不影响另一个

### DT-02: Webhook URL 缺失
- **结果**: ✅ PASS — 企微和钉钉各自独立检查 `if (!webhookUrl) return false`

### DT-03: 钉钉签名时间戳
- **结果**: ✅ PASS — 使用 `Date.now()` 动态生成，钉钉要求 ±5 分钟窗口

### DT-04: 通知重试
- **结果**: ⚠️ 观察 — `fetch` 失败直接返回 `false`，无重试逻辑。网络抖动时可能丢失通知。建议添加指数退避重试（最多 3 次）

### DT-05: 通知限频
- **结果**: ⚠️ 观察 — 同一项目短时间多次构建会发送多条通知，无去重/限频。建议添加 Redis 存储最近通知时间，5 分钟内不重复发送

## 代码质量评审

### 正面发现
1. **类型设计清晰**: `NotificationPayload` 接口覆盖 index:completed/failed、usage:warning、approval:request 四种场景
2. **双通道容错**: `Promise.allSettled` 保证高可用
3. **钉钉签名正确**: HMAC-SHA256 + timestamp + sign 参数拼接符合钉钉规范
4. **审计自记录**: 每次通知发送写入 `NOTIFICATION_SENT` 审计日志
5. **错误隔离**: 通知失败不影响主流程（返回 boolean 由调用方处理）

### 残留问题

| # | 严重度 | 描述 |
|---|--------|------|
| 1 | LOW | 无通知重试机制 — `fetch` 失败直接返回 false，网络波动时通知可能丢失 |
| 2 | LOW | 无通知限频 — 同一项目短时间可能重复通知 |
| 3 | LOW | 审批通知无对应审批操作实现 — 仅发送通知，审批逻辑未实现 |
